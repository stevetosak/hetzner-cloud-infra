This task did the first part of the Phase 6 item "Secrets and services" in the [rebuild Plan](../runbook/rebuild-2026-09-20.md): the secrets root. Bitwarden became the source of every credential at run time, kluster gained `kluster secrets` over a committed Secret Catalog, Reloader was added so a changed Secret restarts its readers, and then every live Secret was rotated. The decisions are the 2026-10-06 Amendment to [ADR 0003](../adr/0003-recoverability.md); the operator-facing procedure is [the Secrets runbook](../runbook/secrets.md). The other parts of the item (`services seed`, `db create`, the rehearsal patch set) moved to new Plan items and are not in this Log.

## The design

The design was agreed with the operator in a 15-question grill on 2026-10-06 and recorded as the Amendment and two glossary terms in [`CONTEXT.md`](../../CONTEXT.md). It follows from the preference that, until the rebuild ends, breaking changes are accepted when they make the cluster safer: live holds no sensitive application and no data worth keeping. That is why every value was made new instead of imported.

A second design pass on 2026-10-10 fixed the shape of the catalog. A key is one of four kinds. `generated` is a random alphanumeric value made by kluster, 40 characters unless the entry says otherwise. `issued` comes from a provider through Bitwarden, by item and field or by attachment. `copy` repeats another key's value, with an optional `format` containing `{value}` (doma's `DATABASE_URL` is built this way). `literal` was added to the design as written in the Amendment: it holds a value that is not secret but must sit inside a Secret, which today is only `db-credentials.username: tosak`. kluster writes `data`, never `stringData`, and re-encrypts the whole file on a change. The encryption check is plain Go: it reads sops metadata and the MAC and requires every value under `data` to be `ENC[…]`, so it needs no key and no sops binary. That is why the pre-commit hook and the new CI job `secrets-check.yml` can both run it.

## What was built, in order

Section 1 gave kluster a Bitwarden source for its environment credentials, then `kluster exec [--env] -- <command>`, which runs a command with an environment's credentials in a cleaned environment (every `TF_*`, `AWS_*`, `HCLOUD_*`, `BW_*` and `RBW_*` variable from the shell dropped) and replaces `source infra/.envrc` for hand-run Terraform. `kluster cp init` now gives the cloud controller its own cluster token, never the Terraform token. The rehearsal moved to the Bitwarden item `kluster/rehearsal`.

Section 2 built the catalog and the commands: `list`, `generate`, `rotate`, `pull`, `set`, `diff`, `apply`, `edit` and `check`. The notes that had lived in the blank `credentials.yaml` templates moved into `secrets.yaml`, the templates and `scripts/secrets.sh` were deleted, and `DB_USER` moved from the `authos` Secret to the authos-api ConfigMap because it is not secret.

The Bitwarden client then changed. The official `bw` CLI starts Node.js on every call, about 3 s, and `secrets list` took 13.6 s. kluster now reads items through `rbw` under its own profile `kluster`, and uses `bw` only for the one attachment, `keystore.p12`, because rbw cannot download attachments (upstream issue doy/rbw#130). The trade-off is a second, unofficial client holding the unlocked vault keys. The mitigations: kluster never unlocks the agent, the operator does, in their own terminal; the profile has its own agent with a `lock_timeout` of 900 s; and kluster strips every `RBW_*` and `BW_*` variable from child processes, so no Terraform or kubectl child can reach the vault. Because `rbw get` falls back to a partial name match, kluster lists the ids once and matches the exact name, and refuses a duplicate.

Reloader (PR #36) is Stakater Reloader chart 2.2.18, Reloader v1.4.22, image pinned by digest, as a pinned helm render in `core/reloader/` applied by hand like cert-manager. Workloads opt in with `secret.reloader.stakater.com/auto: "true"` in their base `deployment.yaml`: `redis`, `authos-api`, `duster` and `doma`. It runs scoped (`watchGlobally: false`, namespaces `redis`, `authos`, `doma` and its own), so the chart creates one Role per namespace and no ClusterRole; a cluster-wide watch would have read every Secret including ArgoCD's and the Cloudflare token. The cost is that a new project that reads a Secret must add its namespace to `core/reloader/reloader-values.yaml` and render again. The `projects` ApplicationSet ignores the pod-template annotation `reloader.stakater.com/last-reloaded-from`, so ArgoCD shows no drift. CloudNativePG, cert-manager and ArgoCD read their Secrets themselves and are not covered.

## What was proven

The Bitwarden path was proven on the real vault on 2026-10-06: `node list --env rehearsal` resolved `kluster/rehearsal` and passed the live-project guard, and `kluster exec --env rehearsal -- terraform -chdir=../../infra/shared plan` read the rehearsal state (old primary IP `2.29.58.131`, not the live `46.62.209.249`; 9 to add). The backend override was proven only from an empty data dir: with the `.tf` files copied to an empty `mktemp -d`, `terraform init` through `kluster exec` wrote `"bucket": "hetzner-cloud-infra-staging"` into the new data dir and `state list` read the rehearsal state. The existing `infra/*/.terraform-rehearsal` directories already pointed at the staging bucket, so a plan through them proves nothing about the override.

The sops behaviour was proven with a throwaway age key, an empty `HOME` and `env -i` (sops 3.13.3): `sops encrypt` needs no private key, and `sops decrypt` fails without one and passes with `SOPS_AGE_KEY` in the child environment only. On 2026-10-20 the operator ran `kluster secrets list` and `pull --apply` through rbw and all four issued values were read. Reloader was applied the same day (namespace, `reloader.yaml` server-side, the Redis Deployment with the annotation only, the ApplicationSet); `kubectl -n reloader rollout status` succeeded and its log showed controllers for Secrets and ConfigMaps in `redis`, `authos`, `doma` and `reloader`.

## The live rotation

The operator ran `kluster secrets pull --apply`, then `generate --apply`, and committed the first six encrypted files (`4ddfec4`). Then `secrets apply --apply` ran per Secret in this order: `pg-cluster/db-credentials`, `redis/redis`, `authos/credentials` with `doma/credentials` (Reloader restarted the readers), then `cert-manager/cloudflare-dns-token` and `argocd/argocd-notifications-secret`. The order is the order of the names on the command line; with no names it is catalog order, which is alphabetical by namespace and not by dependency. Every value is new, with no import.

Two faults showed up. 🔴 The live Secrets had been made with `kubectl create`, so the field manager `kubectl-create` owned `.data.*` and kluster, which never forces, stopped with `conflict with "kubectl-create" using v1: .data.password`. The fix is the opt-in flag `kluster secrets apply --force-conflicts` (PR #37, commit `c32b98a`), needed once per Secret; later applies need no flag. The operator chose it over deleting and re-applying, because a Secret would be briefly absent while CloudNativePG may reconcile.

The second fault: a forced apply does not remove a key that only the old field manager owns, so `DB_USER` stayed on live `authos/credentials` and `secrets apply` ended with "the live Secrets still differ after apply". 🔴 The repo's authos-api ConfigMap already carried `DB_USER`, but the live one did not, because ConfigMaps are applied by hand. The order used was: apply the ConfigMap, restart `deploy/authos-api`, check `DB_USER` has length 5 in the pod, and only then `kubectl -n authos patch secret credentials --type=json -p '[{"op":"remove","path":"/data/DB_USER"}]'`.

The end state was read back on 2026-10-20: `go run . secrets diff` listed all 13 Secrets as in step and exited 0; `kubectl -n pg-cluster get cluster` reported "Cluster in healthy state", 3/3; authos-api, duster and doma were Running 1/1; `kubectl -n argocd get applications` showed all five Synced and Healthy, which also confirms the ApplicationSet's `ignoreDifferences`. The Reloader log showed `Changes detected in 'redis' of type 'SECRET'` followed by an update of the Deployment, and the same for `authos-api`, `duster` and `doma`; the Redis pod was new and `READY 1/1`.
