[ADR 0012](../adr/0012-mail-is-self-hosted-on-stalwart-and-sent-through-amazon-ses.md)
holds the design: Stalwart in the namespace `mail` stores the inboxes, its data
store is the database `mail` on `tosak-pg-cluster`, its message files are in a
versioned Backblaze B2 bucket, mail enters through its own load balancer, and
every outgoing message leaves through Amazon SES in `eu-central-1`. This Plan is
the order of the work. Nothing is built yet.

The order follows the risk. The outside accounts come first, because SES
production access is a request that can take days and can be refused, and
because four facts the design depends on are still unproven. The build and a
rehearsal follow, with no MX record pointing at the server, so nothing outside
can deliver to it by accident. **The live rollout waits for Phase 1 of the
[capacity Plan](./capacity-right-size-then-grow-by-cost.md)**, because the
workers have no room for a new workload until requests are right-sized. That
is a dependency, not a trigger: when the capacity phase is done, the operator
is told, and the operator starts Phase 3.

The project and namespace are `mail`; the image is `stalwartlabs/stalwart`,
pinned by digest; the hosts are `mail.tosak.net` (DNS only, the mail load
balancer), `mail-admin.tosak.net` and `mta-sts.tosak.net` (both proxied, on the
Gateway). The SES SMTP credentials, the two B2 keys and the Stalwart admin
password are issued and live in Bitwarden; the metrics basic-auth password is
generated by kluster.

## Phase 1 — Accounts and open checks

**Done when:** SES has production access in `eu-central-1` and `tosak.net` is a
verified identity with Easy DKIM and the MAIL FROM domain `bounce.tosak.net`;
the B2 bucket exists in an EU region with versioning and a 30-day expiry of old
versions; the CloudWatch alarms send a test message to the admin Gmail address;
and the open checks below each have an answer in the Task Record.

- [ ] Check that Backblaze B2 offers an EU region when the account is created.
      The region is chosen per account and cannot be changed later. If there
      is no EU region, stop and bring the question back to the operator; the
      design assumes one.
- [ ] Create the B2 bucket for the message files with versioning on and a
      lifecycle rule `daysFromHidingToDeleting: 30`, the same window as the
      PostgreSQL backups. Create two application keys scoped to that bucket:
      read and write for Stalwart, read only for the Restore Drill. The
      operator creates both and stores them in Bitwarden under `kluster/`.
- [ ] Set up SES in `eu-central-1`: the identity `tosak.net` with Easy DKIM,
      the custom MAIL FROM domain `bounce.tosak.net` with the MX failure
      behaviour `UseDefaultValue`, SMTP credentials stored in Bitwarden, and
      the request for production access. The DKIM and MAIL FROM records can be
      published now (rows 3 to 7 of the record list below), because they do not
      change where mail for `tosak.net` is delivered.
- [ ] Add the CloudWatch alarms on `Reputation.BounceRate` above 2 % and
      `Reputation.ComplaintRate` above 0.05 %, through an SNS topic to the
      admin Gmail address. Confirm the subscription and send one test alarm.
- [ ] Check that the pinned Stalwart release (0.16 or later) reads its TLS
      certificate and key from files (`%{file:…}%`). If it cannot, the
      fallback is Stalwart's own TLS-ALPN-01, and ADR 0012 gets an amendment
      before the build.
- [ ] Check the rest of the Stalwart configuration against the pinned
      release: PostgreSQL as the data store, B2 through its S3 API as the blob
      store, PROXY protocol with a trusted-networks list, a relay route with
      SMTP authentication to SES, and the Prometheus exporter at
      `/metrics/prometheus` with basic auth.
- [ ] Confirm the current price of an `lb11`. These docs say €5.39 a month; a
      rise in 2026 is reported. Correct ADR 0012 if the price changed.

## Phase 2 — Build and rehearsal

**Done when:** the `mail` project is merged and `kluster services check`
passes; in a rehearsal with no MX record, a message sent over SMTP to the mail
load balancer is read back over IMAP, a message sent through SES reaches a
verified address and passes SPF, DKIM and DMARC, a pod restart during a send
loses no message, every probe and alert fires once on a forced fault, and one
run of the Restore Drill passes its mail phase.

- [ ] Add the project entries that `kluster services check` asks for: the
      namespace file, the AppProject, the generator line, `mail` in the
      Gateway's `allowedRoutes`, and `mail` in Reloader's namespaces with its
      Role and RoleBinding.
- [ ] Add the database `core/cnpg/databases/mail.yaml`, owned by `tosak`, and
      list it in `core/cnpg/kustomization.yaml`.
- [ ] Add the Secrets to the Secret Catalog: SES SMTP, the B2 read-write key
      and the admin password (issued), and the metrics basic-auth password
      (generated); and the B2 read-only key for `pg-drill` (issued).
- [ ] Write the Stalwart Deployment: one replica, no volume, the in-memory
      store in process, the Reloader annotation, a first memory request of
      256 Mi (an estimate, measured in the rehearsal and set by the capacity
      Plan's sizing rule). Its configuration sends every non-local recipient to
      SES on port 587 and never delivers to a foreign MX.
- [ ] Write the `LoadBalancer` Service for 25, 465 and 993 with the Hetzner
      annotations (`lb11`, `hel1`, PROXY protocol on), and set Stalwart's
      trusted networks to the load balancer's source range only.
- [ ] Add the cert-manager `Certificate` for `mail.tosak.net` in `mail`, from
      `letsencrypt-prod`, mounted into the pod.
- [ ] Route `mail-admin.tosak.net` on the Gateway to Stalwart's admin paths
      only, add its Cloudflare Access application (the operator's email only),
      and give it an `http_access` probe target, as Grafana has.
- [ ] Serve the MTA-STS policy at `mta-sts.tosak.net` with an `HTTPRoute` and
      an `HTTPRouteFilter` direct response from a ConfigMap, mode `testing`,
      and check that Cloudflare does not answer the policy fetch with a bot
      challenge.
- [ ] Add monitoring: a ServiceMonitor for the Stalwart exporter (never
      routed), blackbox probes on `mail.tosak.net` ports 25, 465 and 993 with
      certificate expiry, and alert rules to Telegram. Prove that the probes go
      out through the mail load balancer and back with PROXY protocol, not
      straight to the pod.
- [ ] Write the DNS check script: for one domain, `dig` every record in its
      list and read the SES verified status, and fail on any difference.
- [ ] Add the mail phase to the Restore Drill as ADR 0003's amendment of
      2026-11-02 describes: the copy as of the replay end, the throw-away
      Stalwart with no SES credentials, no relay route, the read-only key and
      no Service, the canary `drill@tosak.net` checked by sha256, and K = 20
      random messages.
- [ ] Run the rehearsal and record the measured memory, the proofs in the
      finish line above, and every fault found, in the Task Record.

## Phase 3 — Live rollout for tosak.net

Starts only when Phase 1 of the capacity Plan is done and the operator starts
it.

**Done when:** mail for `tosak.net` is delivered from an outside mailbox and
answered back to it, the DNS check script passes for `tosak.net`, the first
production drill passes its mail phase, the mailboxes `dmarc@tosak.net` and
`drill@tosak.net` exist, and DMARC and TLS reports arrive at `dmarc@`.

- [ ] Sync the `mail` project to the live cluster and note the public IP
      address of the new load balancer.
- [ ] Publish the records for `tosak.net` in Cloudflare by hand, from the list
      below, then run the DNS check script.
- [ ] Create the operator's account, `dmarc@tosak.net` and the canary
      `drill@tosak.net`; deliver the canary message once and record its sha256
      for the drill.
- [ ] Send and receive with an outside mailbox (Gmail) in both directions, and
      read the message headers for SPF, DKIM and DMARC passes.
- [ ] Report to the operator when the TLS reports show no failures; the
      operator decides when to change MTA-STS from `testing` to `enforce`, and
      when to raise DMARC above `p=none`.

The records for `tosak.net`. The first nine are the mail itself; the last five
are MTA-STS, TLS reporting and the autoconfiguration records.

| # | Name | Type | Value | Proxy |
|---|---|---|---|---|
| 1 | `mail.tosak.net` | A | the mail load balancer's IP address | DNS only |
| 2 | `tosak.net` | MX | `10 mail.tosak.net` | — |
| 3–5 | `<token>._domainkey.tosak.net` (three) | CNAME | `<token>.dkim.amazonses.com`, from SES | DNS only |
| 6 | `bounce.tosak.net` | MX | `10 feedback-smtp.eu-central-1.amazonses.com` | — |
| 7 | `bounce.tosak.net` | TXT | `v=spf1 include:amazonses.com ~all` | — |
| 8 | `_dmarc.tosak.net` | TXT | `v=DMARC1; p=none; rua=mailto:dmarc@tosak.net` | — |
| 9 | `mail-admin.tosak.net` | A | the Gateway, as every web host | Proxied |
| 10 | `mta-sts.tosak.net` | A | the Gateway, as every web host | Proxied |
| 11 | `_mta-sts.tosak.net` | TXT | `v=STSv1; id=<policy id>` | — |
| 12 | `_smtp._tls.tosak.net` | TXT | `v=TLSRPTv1; rua=mailto:dmarc@tosak.net` | — |
| 13 | `_imaps._tcp.tosak.net` | SRV | `0 1 993 mail.tosak.net` | — |
| 14 | `_submissions._tcp.tosak.net` | SRV | `0 1 465 mail.tosak.net` | — |

## Phase 4 — Client domains

Starts when the operator takes on the first client domain.

**Done when:** a Procedure page describes how a client domain is added, and the
first client domain passes the DNS check script and sends and receives with an
outside mailbox.

- [ ] Write the record list a client publishes in their own zone: rows 2 to 8
      above for their domain, with the MX pointing to `mail.tosak.net` (seven
      records). The client writes them; the check script proves them.
- [ ] Write the Procedure `Add a client mail domain`: the SES identity with
      Easy DKIM and its MAIL FROM domain, the domain in Stalwart, the
      accounts and their quotas (the operator creates every client account),
      the record list for the client, and the check script.
- [ ] Onboard the first client domain with that Procedure, and correct the
      Procedure from what the first run finds.

## Deferred decisions

Each of these is the operator's to take, at a time the operator chooses. None
of them starts on a condition by itself.

- A second Stalwart pod. Worth raising once a paying client has mailboxes. It
  moves the in-memory store to the shared Redis; first check that Stalwart sets
  a TTL on every key it writes, because that Redis evicts only keys with a TTL
  and Authos shares it.
- Stalwart Enterprise, for tenants and per-tenant admins. A license key on the
  same binary, with no data migration.
- Webmail. If one is wanted, check Bulwark Webmail first (JMAP, made for
  Stalwart, needs Stalwart 0.16 or later).
- MTA-STS for client domains, and DANE for any domain.
- How the applications send mail: through Stalwart's submission port or
  straight to SES.
- DNS records written by automation instead of by hand. Stalwart's own
  automatic DNS is rejected, because it needs a zone token in a pod that faces
  the internet.
- A sampled drill copy instead of the full one, when the full copy becomes
  heavy.
