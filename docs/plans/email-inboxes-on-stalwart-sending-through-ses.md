[ADR 0012](../adr/0012-mail-is-self-hosted-on-stalwart-and-sent-through-amazon-ses.md)
holds the design: Stalwart in the namespace `mail` stores the inboxes, its data
store is the database `mail` on `tosak-pg-cluster`, its message files are in a
versioned Scaleway Object Storage bucket in `nl-ams` (B2 until the ADR's
amendment of 2026-11-08), mail enters through its own load balancer, and
every outgoing message leaves through Amazon SES in `eu-central-1`. This Plan is
the order of the work. Nothing is built yet.

The order follows the risk. The outside accounts come first, because SES
production access is a request that can take days and can be refused, and
because four facts the design depends on are still unproven. The build and a
rehearsal follow, with no MX record pointing at the server, so nothing outside
can deliver to it by accident. **The live rollout waits for Phase 1 of the
[capacity Plan](./capacity-right-size-then-grow-by-cost.md)**, because the
workers have no room for a new workload until requests are right-sized. That
is a dependency, not a trigger: when the capacity phase is done, the operator
is told, and the operator starts Phase 3.

The project and namespace are `mail`; the image is
`stalwartlabs/stalwart:v1.0.3`, pinned by digest
(`sha256:73c684a84c24f5b4206ec266a8deb8986fe44a9f623997e07f084388d943c8bd`); the hosts are `mail.tosak.net` (DNS only, the mail load
balancer), `mail-admin.tosak.net` and `mta-sts.tosak.net` (both proxied, on the
Gateway). The SES SMTP credentials, the four bucket keys and the Stalwart
admin password are issued and live in Bitwarden; the metrics basic-auth password is
generated by kluster.

## Phase 1 — Accounts and open checks

**Done when:** SES has production access in `eu-central-1` and `tosak.net` is a
verified identity with Easy DKIM and the MAIL FROM domain `bounce.tosak.net`;
the live and rehearsal buckets exist on Scaleway in `nl-ams` with versioning
and a 30-day expiry of old versions, and their four keys are in Bitwarden under
`kluster/`; SES sends the bounce and complaint notifications of `tosak.net` to
an SNS topic that the admin Gmail address receives; the CloudWatch alarms send
a test message to the admin Gmail address; and the open checks below each have
an answer in the Task Record.

- [x] Check that Backblaze B2 offers an EU region when the account is created.
      The region is chosen per account and cannot be changed later. If there
      is no EU region, stop and bring the question back to the operator; the
      design assumes one. **Done 2026-11-07**: B2 offers EU Central
      (Amsterdam); one region per account, chosen at sign-up and never changed
      (Backblaze's data-regions page). **Overturned 2026-11-08**: the live
      sign-up form offered only CA East, US East and US West. The operator
      chose Scaleway instead; ADR 0012 has an amendment.
- [x] Create the Scaleway account on the admin Gmail address with two-factor
      authentication, and two Projects: `mail` and `mail-rehearsal`, one bucket
      each in `nl-ams`, Standard Multi-AZ (`tosak-mail-blobs` and
      `tosak-mail-blobs-rehearsal`). Each bucket is private, has versioning on,
      SSE-ONE encryption, and a lifecycle rule with
      `NoncurrentVersionExpiration` after 30 days (the same window as the
      PostgreSQL backups), `ExpiredObjectDeleteMarker` and an abort of
      incomplete multipart uploads; the console sets all three. Each Project
      gets two IAM applications, each with its own policy scoped to that
      Project only: read and write for Stalwart with the permission sets
      `ObjectStorageObjectsRead`, `ObjectStorageObjectsWrite`,
      `ObjectStorageObjectsDelete` and `ObjectStorageBucketsRead`, and
      `ObjectStorageReadOnly` for the Restore Drill; IAM grants per Project, so
      this scopes each key to one bucket. The operator stores the four keys in
      Bitwarden as `kluster/scw-mail`, `kluster/scw-mail-readonly`,
      `kluster/scw-mail-rehearsal-rw` and `kluster/scw-mail-rehearsal-ro`
      (fields `access_key_id`, `secret_access_key`). Then each key is checked
      without reading its value: byte lengths, a bucket listing with the
      read-only key, a refused write with it, and the versioning and lifecycle
      read back from each bucket. **Done 2026-11-14**: every key is 20 and 36
      bytes and lists only its own bucket (the other Project's bucket answers
      `AccessDenied`); a `PUT` with each read-only key was refused and left
      both buckets empty; both buckets read back versioning `Enabled`, the rule
      `expire-old-versions` (`NoncurrentDays` 30, `ExpiredObjectDeleteMarker`,
      multipart abort after 7 days, no expiry of current versions) and default
      encryption `AES256`; `ListObjectVersions` works with both read-only keys.
      The requests were signed with a standard-library SigV4 signer, because
      the laptop's curl 7.81 `--aws-sigv4` signs S3 requests wrongly.
- [x] Set up SES in `eu-central-1`: the identity `tosak.net` with Easy DKIM,
      the custom MAIL FROM domain `bounce.tosak.net` with the MX failure
      behaviour `UseDefaultValue`, SMTP credentials stored in Bitwarden, and
      the request for production access. The DKIM and MAIL FROM records can be
      published now (rows 3 to 7 of the record list below), because they do not
      change where mail for `tosak.net` is delivered. Row 8 went up early too,
      on 2026-11-09, as `v=DMARC1; p=none` without `rua`, because the SES
      recommendations flagged the missing record; `p=none` changes no
      delivery, and a report address is useless until `dmarc@` exists
      (checked on both Cloudflare nameservers and 8.8.8.8). **Done
      2026-11-14**: the console shows the identity Verified, DKIM Successful
      and the custom MAIL FROM domain Successful (2026-11-08); the SMTP
      credentials are in `kluster/mail-ses-smtp` (a 20-byte SMTP user name and
      a 44-byte password, checked by length); AWS granted production access
      in `eu-central-1` on the support case, with a quota of 50,000 messages a
      day at 14 a second.
- [x] Route the bounce and complaint notifications of `tosak.net` to an SNS
      topic `mail-alerts` in `eu-central-1` with the admin Gmail address
      subscribed, turn email feedback forwarding off until Phase 3, and check
      that the account-level suppression list is on for bounces and
      complaints. SES requires a process for bounces and complaints; without
      one it mails each notification to the message's Return-Path or sender
      address, and the Service Terms (section 15.4, 2026-11-05) let AWS
      suspend sending when that address does not receive mail. `tosak.net`
      has no MX until Phase 3. Prove it with one console test send each to
      `bounce@simulator.amazonses.com` and
      `complaint@simulator.amazonses.com`: each gives one notification in
      Gmail. Simulator sends count against neither the quota nor the
      reputation rates. **Done 2026-11-14**: the console test sends with the
      Bounce and Complaint scenarios each gave one SNS mail in Gmail, carrying
      the raw notification JSON. Read back with the AWS CLI: `mail-alerts` is a
      Standard topic with one confirmed Email subscription; the identity's
      `BounceTopic` and `ComplaintTopic` are `mail-alerts` and
      `ForwardingEnabled` is `false`; the account's suppression list holds
      `BOUNCE` and `COMPLAINT`, and its enforcement status is `HEALTHY`. The
      topic must be Standard: a FIFO topic offers only SQS as a subscription
      protocol, and a topic's type cannot change after it is created.
- [x] Add the CloudWatch alarms on `Reputation.BounceRate` above 2 % and
      `Reputation.ComplaintRate` above 0.05 % (AWS reviews an account at 5 %
      and 0.1 %, and may pause it at 10 % and 0.5 %), through the same
      `mail-alerts` topic. Send one test alarm with
      `aws cloudwatch set-alarm-state`: a simulated bounce does not move the
      reputation metrics. **Done 2026-11-14**: the alarms
      `ses-bounce-rate-above-2pct` (threshold `0.02`) and
      `ses-complaint-rate-above-0.05pct` (threshold `0.0005`) take the
      Maximum over one hour and treat missing data as not breaching, because
      the reputation metrics appear only after the first real bounce or
      complaint; they were made with the CLI for the same reason, since the
      console's metric picker lists only metrics that exist. `set-alarm-state`
      moved each to `ALARM`, the alarm history shows the SNS action executed,
      and Gmail received both alarm mails.
- [x] Check that the pinned Stalwart release reads its TLS certificate and
      key from files. If it cannot, the fallback is Stalwart's own
      TLS-ALPN-01, and ADR 0012 gets an amendment before the build.
      **Done 2026-11-07**: the pin is 1.0.3, not "0.16 or later" (1.0 has a
      new database layout; a 0.16 store cannot be upgraded in place). A
      `Certificate` object takes `certificate` and `privateKey` as
      `{"@type": "File", "filePath": "…"}`; a replaced file is read again
      only after `Action/ReloadTlsCertificates` or a restart, which Reloader
      gives. No fallback is needed.
- [x] Check the rest of the Stalwart configuration against the pinned
      release: PostgreSQL as the data store, an S3 bucket as the blob
      store (B2 at the time; Scaleway speaks the same API), PROXY protocol
      with a trusted-networks list, a relay route with SMTP authentication to
      SES, and the Prometheus exporter at
      `/metrics/prometheus` with basic auth. **Done 2026-11-07**, from the
      1.0 documentation and the source at tag `v1.0.3`: each is supported.
      🔴 In 1.0 only the bootstrap file `config.json` (the data store
      connection) is a file. Every other setting lives in the data store and
      is applied through the API with `stalwart-cli apply` from an NDJSON
      plan; the Phase 2 steps below carry what this changes.
- [x] Confirm the current price of an `lb11`. These docs say €5.39 a month; a
      rise in 2026 is reported. Correct ADR 0012 if the price changed.
      **Done 2026-11-07**: €7.49 a month excluding VAT since Hetzner's price
      change of 2026-04-01; ADR 0012 has an amendment.

## Phase 2 — Build and rehearsal

**Done when:** the `mail` project is merged and `kluster services check`
passes; in a rehearsal with no MX record, a message sent over SMTP to the mail
load balancer is read back over IMAP, a message sent through SES reaches a
verified address and passes SPF, DKIM and DMARC, a pod restart during a send
loses no message, every probe and alert fires once on a forced fault, and one
run of the Restore Drill passes its mail phase. Bounce and complaint tests go
to the SES mailbox simulator, never to an invented address: AWS counts a
bounce from an invented address against the account.

- [ ] Add the project entries that `kluster services check` asks for: the
      namespace file, the AppProject, the generator line, `mail` in the
      Gateway's `allowedRoutes`, and `mail` in Reloader's namespaces with its
      Role and RoleBinding.
- [ ] Add the database `core/cnpg/databases/mail.yaml`, owned by `tosak`, and
      list it in `core/cnpg/kustomization.yaml`.
- [ ] Add the Secrets to the Secret Catalog: SES SMTP, the Scaleway
      read-write key and the admin password (issued), and the metrics
      basic-auth password (generated); and the Scaleway read-only key for
      `pg-drill` (issued). Each bucket key's `rehearsalItem` names its
      rehearsal key (`kluster/scw-mail-rehearsal-rw`,
      `kluster/scw-mail-rehearsal-ro`).
- [ ] Write the Stalwart Deployment: one replica with `strategy: Recreate`,
      no volume, the in-memory store in process, the Reloader annotation, a
      first memory request of 256 Mi (an estimate, measured in the rehearsal
      and set by the capacity Plan's sizing rule). Each process leases a node
      ID in the data store and keeps its in-memory store to itself, so two
      pods must never overlap; Recreate prevents a rolling update from
      starting the second one. The bootstrap `config.json` (the `PostgreSql`
      data store, its password from a file) comes from a ConfigMap. The
      probes are Stalwart's own: `/healthz/live` and `/healthz/ready` on the
      HTTP listener 8080. The container runs as UID 2000 and keeps
      `NET_BIND_SERVICE` under `drop: [ALL]`.
      - [ ] Write the Stalwart settings as an NDJSON plan in git, and decide
        how it is applied (the first start runs in recovery mode with the
        issued admin password; later applies use the API). The plan sets the blob store to
        `S3` explicitly, because `Default` keeps the message files in the data
        store; it sends every non-local recipient to the relay route `ses`
        (`email-smtp.eu-central-1.amazonaws.com`, port 587, STARTTLS, SMTP
        authentication) through the outbound strategy's `route` expression, and
        never delivers to a foreign MX; and it enables the Prometheus exporter
        with basic auth. The full-text index then lives in PostgreSQL (the
        search store's default); the rehearsal measures what that adds.
- [ ] Write the `LoadBalancer` Service for 25, 465 and 993 with the Hetzner
      annotations (`lb11`, `hel1`, PROXY protocol on), and set the trusted
      networks on the listeners for 25, 465 and 993 only
      (`overrideProxyTrustedNetworks`), to the source range the pod sees
      behind the load balancer. A connection from a trusted network without a
      PROXY header is closed, and the global list would also exempt that range
      from auto-ban.
- [ ] Add the cert-manager `Certificate` for `mail.tosak.net` in `mail`, from
      `letsencrypt-prod`, mounted into the pod.
- [ ] Route `mail-admin.tosak.net` on the Gateway to Stalwart's admin paths
      only, add its Cloudflare Access application (the operator's email only),
      and give it an `http_access` probe target, as Grafana has.
- [ ] Serve the MTA-STS policy at `mta-sts.tosak.net` with an `HTTPRoute` and
      an `HTTPRouteFilter` direct response from a ConfigMap, mode `testing`,
      and check that Cloudflare does not answer the policy fetch with a bot
      challenge.
- [ ] Add monitoring: a ServiceMonitor for the Stalwart exporter (never
      routed), blackbox probes on `mail.tosak.net` ports 25, 465 and 993 with
      certificate expiry, and alert rules to Telegram. Prove that the probes go
      out through the mail load balancer and back with PROXY protocol, not
      straight to the pod.
- [ ] Write the DNS check script: for one domain, `dig` every record in its
      list and read the SES verified status, and fail on any difference.
- [ ] Add the mail phase to the Restore Drill as ADR 0003's amendment of
      2026-11-02 describes: the copy as of the replay end, the throw-away
      Stalwart with no SES credentials, no relay route, the read-only key and
      no Service, the canary `drill@tosak.net` checked by sha256, and K = 20
      random messages. 🔴 In Stalwart 1.0 the restored `mail` database also
      holds every setting, including the relay route and the blob store that
      points at the production bucket. The drill Stalwart must replace those
      settings before any mail service starts, for example by starting in
      recovery mode (only the management listener runs, according to the
      documentation; the build proves it) and applying a drill plan first.
- [ ] Run the rehearsal and record the measured memory, the proofs in the
      finish line above, and every fault found, in the Task Record. A
      rehearsal ran no application and no drill until 2026-11-14, so the
      operator chose to teach it a list of rehearsed projects first
      ([ADR 0010, Amendment 2026-11-14](../adr/0010-argocd-syncs-core-and-kluster-only-seeds-it.md#amendments)).
      Done when the finish line above holds in one rehearsal run and
      `kluster --env rehearsal down --apply` reads the project back empty.
      - [x] Rehearsed projects in kluster: the rehearsal `projects`
        ApplicationSet with `mail` from `overlays/rehearsal` (the dev overlay,
        the mail load balancer and the rehearsal bucket), its Namespace and

      - [ ] Push the branch `rehearsal`, run `kluster --env rehearsal up --db

      - [ ] Prove the finish line: SMTP in through the load balancer and IMAP

## Phase 3 — Live rollout for tosak.net

Starts only when Phase 1 of the capacity Plan is done and the operator starts
it.

**Done when:** mail for `tosak.net` is delivered from an outside mailbox and
answered back to it, the DNS check script passes for `tosak.net`, the first
production drill passes its mail phase, the mailboxes `dmarc@tosak.net` and
`drill@tosak.net` exist, and DMARC and TLS reports arrive at `dmarc@`.

- [ ] Before the merge, put in place everything the merge's probes test
      that is applied by hand, so that `MailPortDown` and `PublicHostDown` do
      not page (operator, 2026-11-14). The merge of `feat/mail` makes Argo
      CD sync the probes and alert rules at once, while the parts they test
      come by hand. From the `feat/mail` work tree: seed the namespace `mail`
      and its Secrets (`go run . services seed --env live --apply` in
      `tools/kluster`); apply the load balancer (it buys `mail-lb`, so the
      operator approves it first) and note its public IP address; apply the
      ClusterIP Service, `httproute.yaml` and the `Certificate`, so that
      `mail-tls` exists before the pod; create the Cloudflare Access
      application for `mail-admin.tosak.net`; and publish rows 1, 9 and 10
      of the list below. Until the merge, the Gateway refuses the routes,
      because its allow list on `master` does not name `mail` yet.
- [ ] Merge `feat/mail`. Argo CD syncs the project, the Gateway's allow list,
      the probes and the rules. Check that the pod is ready and every mail
      and host probe passes within the five minutes before the alerts fire;
      `core-gateway` and `core-monitoring` sync on their own, so the routes
      can lag the probes by one sync. Rebuild the installed `kluster` binary,
      which refuses the new port probes until it has the probe-job filter.
- [ ] Publish the other records for `tosak.net` in Cloudflare by hand, from
      the list below, then run the DNS check script. Row 8 passes only after
      the next step adds its `rua`.
- [ ] Create the operator's account, `dmarc@tosak.net` and the canary
      `drill@tosak.net`; deliver the canary message once and record its sha256
      for the drill. Then add `rua=mailto:dmarc@tosak.net` to the DMARC record
      (row 8), which went up early without it.
- [ ] Send and receive with an outside mailbox (Gmail) in both directions, and
      read the message headers for SPF, DKIM and DMARC passes.
- [ ] Turn SES email feedback forwarding on for `tosak.net` once its MX
      points at Stalwart, so a sender learns of a bounce in their own inbox;
      the SNS topic keeps the operator's copy.
- [ ] Report to the operator when the TLS reports show no failures; the
      operator decides when to change MTA-STS from `testing` to `enforce`, and
      when to raise DMARC above `p=none`.

## Deferred decisions

Each of these is the operator's to take, at a time the operator chooses. None
of them starts on a condition by itself.

- A second Stalwart pod. Worth raising once a paying client has mailboxes. It
  moves the in-memory store to the shared Redis; first check that Stalwart sets
  a TTL on every key it writes, because that Redis evicts only keys with a TTL
  and Authos shares it.
- Stalwart Enterprise, for tenants and per-tenant admins. A license key on the
  same binary, with no data migration.
- Webmail. If one is wanted, check Bulwark Webmail first (JMAP, made for
  Stalwart, needs Stalwart 0.16 or later).
- MTA-STS for client domains, and DANE for any domain.
- How the applications send mail: through Stalwart's submission port or
  straight to SES.
- DNS records written by automation instead of by hand. Stalwart's own
  automatic DNS is rejected, because it needs a zone token in a pod that faces
  the internet.
- A sampled drill copy instead of the full one, when the full copy becomes
  heavy.
